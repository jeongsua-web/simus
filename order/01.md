# SIM:US AWS EC2 운영 배포 환경 구축

SIM:US 프로젝트에 GitHub Actions + GHCR + AWS EC2 + Docker Compose 기반의 운영 배포 환경을 구축하려고 한다.

현재 설정된 전문 에이전트를 적극적으로 활용하되, 각 에이전트의 담당 범위를 명확히 분리하고 결과를 통합해라.

## 1. 프로젝트 환경

- 프로젝트 루트: `02_SIMUS`
- 웹/API: Next.js 16.3.8, React 19, TypeScript
- Node.js: 24
- 데이터베이스: PostgreSQL 16
- Unity WebGL: `web/public` 및 관련 배포 스크립트
- 개발용 Compose: 루트 `compose.yaml`
- Next.js 설정: `web/next.config.ts`
- DB 스키마: `db/001_initial_schema.sql` ~ `010_session_npc_motion.sql`
- 운영 서버: AWS EC2 Ubuntu, x86_64, t3.small
- 컨테이너 레지스트리: GHCR
- GitHub 저장소: `jeongsua-web/simus`

## 2. 에이전트별 역할

### backend — 배포 아키텍처 담당
- Next.js API, 실시간 통신, 환경변수 구조 분석
- 프로덕션용 Dockerfile 설계
- 멀티스테이지 빌드 및 standalone 설정 검토
- GitHub Actions의 linux/amd64 빌드 및 GHCR 업로드 설계
- `compose.prod.yaml` 설계
- 기존 개발 환경과 운영 환경 분리
- Unity WebGL 정적 파일의 이미지 포함 방식 검토

### database — PostgreSQL 담당
- 현재 SQL 스키마와 초기화 방식 분석
- 운영 DB의 영속 볼륨 및 백업 전략 검토
- DB 포트 외부 노출 방지
- 운영용 환경변수 및 인증정보 관리
- 기존 SQL 파일과 마이그레이션 적용 방식 검토
- 신규 마이그레이션 파일의 실행 및 적용 이력 관리 방안 제시
- 기존 데이터 보존 방안 수립

### qa — 독립 검증 담당
- Dockerfile 및 Compose 구성 검토
- Next.js 프로덕션 빌드 호환성 확인
- Unity WebGL 파일 누락 가능성 검토
- 환경변수 및 비밀정보 노출 위험 검토
- DB 데이터 삭제 및 초기화 위험 검토
- WebSocket, API, NPC 이벤트 기능의 회귀 테스트 계획
- 배포 실패 시 롤백 방안 검토

필요한 경우에만 unity 또는 web-ui 에이전트를 추가로 호출한다. blender 에이전트는 사용하지 않는다.

## 3. 목표 구성

다음 파일 구성을 우선 검토한다.

- `web/Dockerfile`
- `web/.dockerignore`
- `web/next.config.ts`
- `compose.prod.yaml`
- `.github/workflows/docker-publish.yml`
- 운영 환경변수 예시 파일
- 운영 배포 및 복구 문서

기존 `compose.yaml`은 개발용으로 유지한다.

GitHub Actions는 이미지를 GHCR에 업로드하는 역할까지만 수행하고, EC2 배포는 초기에는 수동으로 진행한다.

## 4. 핵심 요구사항

1. 기존 개발 환경을 손상시키지 않는다.
2. 프로덕션 환경에서 `npm run dev`를 사용하지 않는다.
3. Docker 이미지에 `.env.local`이나 비밀정보를 포함하지 않는다.
4. PostgreSQL의 5432 포트를 외부에 공개하지 않는다.
5. DB 데이터는 컨테이너 재생성 후에도 유지되어야 한다.
6. DB 마이그레이션은 기존 데이터를 삭제하지 않는 방향으로 설계한다.
7. Unity WebGL 정적 파일과 실제 배포 경로를 확인한다.
8. Next.js API, WebSocket, NPC 이벤트 기능의 정상 작동을 고려한다.
9. GHCR 이미지 태그는 버전 추적과 롤백이 가능하도록 설계한다.
10. EC2 t3.small의 메모리 제약을 고려한다.
11. DB 백업과 복구 절차를 포함한다.
12. 실제 배포에 필요한 환경변수 목록을 정리하되 비밀값은 출력하지 않는다.

## 5. 작업 절차 및 승인 규칙

### Phase 1 — 분석 및 계획 보고

먼저 프로젝트의 실제 코드를 조사한다.

- `AGENTS.md`와 각 에이전트 설정 파일 확인
- 기존 Compose 및 Next.js 설정 분석
- 환경변수 이름과 사용 위치 분석
- API, 실시간 통신, Unity WebGL 연동 구조 확인
- DB 초기화 및 마이그레이션 현황 확인
- 기존 CI/CD 설정 확인

각 전문 에이전트의 분석 결과를 통합하여 다음을 보고한다.

1. 현재 프로젝트 배포 구조
2. 발견된 위험 요소
3. 추가 및 수정할 파일 목록
4. Docker 이미지 설계
5. PostgreSQL 운영 및 마이그레이션 전략
6. 검증 방법
7. 예상 리소스 사용 및 제약
8. 사용자에게 필요한 AWS/GitHub 설정

**이 단계에서는 어떤 파일도 수정하지 않는다.**

보고서를 제출한 뒤 내 승인을 기다린다.

### Phase 2 — 구현

내가 승인한 경우에만 설정 파일을 작성하거나 수정한다.

- 기존 기능 및 개발 설정 유지
- 최소한의 변경 적용
- 민감정보 제외
- 변경 파일과 변경 이유 보고

### Phase 3 — 검증

구현이 완료되면 검증 계획을 먼저 보고하고 승인을 기다린다.

승인 후 가능한 빌드 및 테스트를 수행한다.

qa 에이전트가 독립적으로 결과를 검토한다.

### Phase 4 — 배포

실제 Git push, GHCR 이미지 업로드, EC2 접속 및 배포는 모두 별도 승인을 받은 후 진행한다.

DB 초기화, 볼륨 삭제, 데이터 변경, 파괴적 마이그레이션은 사전 승인 없이 절대 수행하지 않는다.

## 6. 최종 목표

GitHub에서 Docker 이미지를 빌드하고 GHCR에 저장한 뒤, EC2에서 해당 이미지를 가져와 SIM:US를 실행할 수 있어야 한다.

또한 기존 참가자 데이터, NPC 상태, 회차 결과를 보존하면서 향후 애플리케이션과 DB 스키마를 안전하게 업데이트할 수 있어야 한다.

**지금은 Phase 1만 수행하고, 분석 보고서를 제출한 뒤 중단해라.**
