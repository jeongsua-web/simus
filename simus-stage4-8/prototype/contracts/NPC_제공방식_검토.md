# 모바일 본인 NPC 추적 제공 방식 검토

2026-09-24. 현재 서버에는 참여자별 NPC ID, 공유 위치, 경로/맵 버전 API가 없다.
Unity의 캡슐 3개는 미리보기이므로 모바일과 같은 NPC라고 주장할 수 없다.

| 방식 | 구현·운영 특성 | 이 프로젝트의 판단 |
|---|---|---|
| 모바일 브라우저에서 경량 2D/3D 도시 렌더 | 각 휴대폰이 본인 NPC를 추적. 공유 경로/기준 시각과 지도 좌표 API 필요. 단말 성능·배터리 확인 필요 | 우선 후보. 2D Canvas 최소 연결 실험을 수행했으나 실제 맵 3D 성능은 미측정 |
| Unity WebGL 모바일 | 기존 도시 자산 재사용 가능. 초기 다운로드·메모리·발열·브라우저 호환성 검증 필요 | 현재 모바일 빌드·최적화 결과가 없어 보류 |
| 전시장 렌더 영상을 참여자별 스트리밍 | 휴대폰 부담 작음. 참여자마다 다른 추적 카메라와 서버 GPU·인코딩·동시 접속 비용 필요 | 예상 인원/비용 미정이므로 보류 |
| 정적/주기적 이미지 | 구현 단순. 연속 추적과 주변 도시 탐색 경험 제한 | 요구사항 F25의 기본 화면으로는 부족 |

`integration/npc_lab.py`는 **독립 모의 서버**다. 두 쿠키에 서로 다른 opaque NPC ID를
발급하고 같은 round ID, Unity XZ m 좌표, 경로(-64,12)↔(-64,45), 속도 2m/s,
server_time/epoch/phase를 내려준다. 새로고침 뒤 같은 쿠키의 ID를 복원하며
`client/lab/index.html`은 자기 ID 위치를 2D Canvas로 따라간다. 100회 로컬 HTTP
왕복 중앙값 0.3ms, p95 0.4ms였다. 네트워크·실제 3D 렌더·다수 동시 접속을
측정한 값은 아니다.

다음 구현 조건은 서버의 회차별 참여자↔NPC ID 바인딩, 공개 경로·맵 버전·위치
기준의 확정이다. 브라우저가 받은 본인 ID를 Unity가 표시하는 ID와 동일하게
대조하고, 재접속·새 회차·종료 동결을 확인해야 동기화 검증 완료로 표시할 수 있다.
단말 지원 범위와 허용 지연 목표도 사용자와 결정한다.
