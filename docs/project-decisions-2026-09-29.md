## 모바일 도시 구현 추천안 — 아직 채택/실측 전

**우선 검증 후보: Three.js 기반 경량 3D 도시 + HTML 선택 패널.** Blender 자산을 모바일용 GLB로 제공하고 전시장 Unity와 회차·NPC ID·경로·서버 시간을 공유한다. 기존 사본에는 약 5.7MB GLB가 있지만 모바일 성능 합격 증거는 아니다.

참여 경험은 본인 캐릭터를 따라가는 카메라, 주변 도시 탐색, 선택에 대한 짧은 반응, 누적 도시 변화, 종료 후 내 캐릭터/도시 공개로 구성한다. 2D로 단순화하는 것을 자동 기본값으로 채택하지 않는다.

| 후보 | 적합성 판단 | 남은 검증 |
|---|---|---|
| Unity Web 빌드 | 기존 장면/연출 재사용 장점. Unity 6000.3은 일부 Android Chrome/iOS Safari를 공식 지원하므로 모바일 불가로 단정하지 않음 | 실제 맵의 초기 다운로드·시작 시간·메모리·발열·중단 복귀 |
| Three.js 경량 3D | 필요한 렌더링과 웹 UI를 개별 조절하기 좋아 우선 후보. 더 빠르다는 보장은 실측 전 불가 | 동일 장면/카메라/기기 조건으로 로딩·프레임·메모리 비교 |
| 2.5D/2D | 저성능 기기 대응 후보. 추적/주변 도시/재미 충족 여부를 별도 평가 | 체험 품질 확인 후 채택 판단 |
| 참여자별 Unity 스트리밍 | 사용자 우려와 비용/동시 접속 조건상 우선 후보에서 후순위 | 현 시점 구현 선택하지 않음 |

최적화 설계 후보: 구역별 자산 로딩, 메시 병합/반복 오브젝트 인스턴싱, 조명 베이크, 텍스처 축소·압축, 기기별 렌더 해상도 조정, 화면 밖 NPC 생략. 500명의 위치를 매 프레임 서버에서 전송하지 않고 공유 경로와 기준 시각으로 각 화면에서 보간하는 방식을 검토한다. 참여자 수와 한 화면에 그릴 캐릭터 수는 구분한다.

10/1까지 동일 맵의 짧은 체험 비교를 목표로 한다. Android/iPhone에서 첫 도시 조작 가능 시간, 선택 UI 응답, 지속 프레임, 10분 발열/안정성, 백그라운드 복귀를 측정한다. 제안 목표는 제한된 모바일 네트워크 조건에서 첫 체험 5초 이내, 정상 진행 30fps 이상이며 기기/전송 속도/측정 비율을 정한 후 인수 기준으로 승인한다. 현재 통과한 수치가 아니다. 사용자는 재미를 확인하고 기술 선택은 측정 결과에 따라 확정한다.

공식 근거(9/29 조회): [Unity 6000.3 모바일 브라우저 지원](https://docs.unity.com/en-us/engine/6000.3/manual/platform-specific/webgl/intro/browsercompatibility), [Three.js 렌더 해상도 제어](https://threejs.org/manual/pages/responsive.html), [오브젝트 최적화](https://threejs.org/manual/pages/optimize-lots-of-objects.html). 지원 목록은 SIMUS 자산 성능 보증이 아니다.

## 장비·배포 추천안 — 미확정

- 관리자 웹은 두 후보 모두 대상으로 두되, 전시장 렌더와 분리된 기기를 우선 사용한다. 일단 Galaxy Book5 Pro를 관리자 후보, MacBook M1을 Unity macOS 빌드 검증 후보로 배치한다. 이는 두 기기의 성능 우열 결론이 아니며, 실제 동시 사용 가능 여부·메모리·모니터 연결 확인이 필요하다.
- Unity 출력은 우선 단일 가로 1920×1080 시험. 현장 디스플레이 수·규격은 아직 미정이다. 새 PC 구매를 전제하지 않는다.
- 참여자는 같은 Wi-Fi에 묶지 않는다. 공개 HTTPS로 개인 데이터와 Wi-Fi에서 접근하는 구조를 검토한다. 기존 네트워크 질문의 목적은 전시장 내부 주소만 배포하는 실수를 피하기 위한 것이었다.
- 기존/학교 제공 상시 서버가 있으면 비용 최소화 후보로 우선 검토. 없다면 무료 계층과 단기 유료 서버를 실제 제한/부하 기준으로 비교한다. 정기 종료 작업을 지속 실행할 수 있어야 한다.
- Vercel Hobby Cron은 공식 문서상 하루 1회이므로 이를 초 단위 자동 종료 스케줄러로 채택하지 않는다. 무료 웹+DB만 골라 운영 준비 완료라고 판단하지 않는다. [공식 제한](https://vercel.com/docs/cron-jobs/usage-and-pricing).
- PostgreSQL의 호스팅/버전/백업은 기술 검토 항목이다. DB 종류를 다시 질문하지 않는다. 일일·행사 전후 백업 및 별도 위치 보관/복원 시험을 추천한다. 보관 기간·허용 복구 손실은 미정.
- 최대 동시 접속 미정 동안 500명 동시 접속은 보수적인 시험 후보로만 둔다. 0.5초 폴링 500명은 엔드포인트 1개만으로도 초당 1,000요청이므로 Unity의 폴링 주기를 모바일 전체에 그대로 적용하지 않는다.

## 추가 결정 — 알림·콘텐츠·3일 운영

### 사용자 확정

- 기본 외부 알림은 웹 푸시. 해당 회차 수신 동의자 전체가 대상이며 미응답자를 제외하지 않는다. 이메일은 가능하면 추가하는 선택 범위다. 계정·운영 총괄은 정수아다.
- 다른 기기에서도 본인의 결과를 열 수 있어야 한다. 타인 결과의 공개 허용을 뜻하지 않는다.
- 결과 저장(이미지 다운로드 등)은 시간·자원이 남으면 추가한다. 서버의 확정 결과 보존은 기존 필수 기능으로 유지한다.
- 콘텐츠 기준은 실제 경로 `docs/choice.md`: 상황 30개, 선택지 91개. 기존 5×2 추천안은 폐기한다. 문구·점수 원본을 임의 변경하지 않는다.
- 전시 3일, 하루 1회차, 총 3회차. 각 1~2시간. 정확한 전시 날짜/시작 시각·회차별 시간은 아직 미정. 10/20이 3일 전시 중 어느 날인지는 확인되지 않았다.
- 입장은 회차 종료 전까지. 개별 선택의 시간제한과 종료 5초 전 선마감은 사용자 의도에 맞게 제거할 대상이다. 사용자 추가 확인: 회차 종료 후에는 미제출 선택도 받지 않는다.
- 나머지 운영·기술 세부사항은 에이전트에게 위임. 비용 지출이나 계정 생성 승인으로 확대하지 않는다.

### 실제 콘텐츠·코드 충돌

`choice.md`는 이미 30개 상황을 제공한다. 도시 점수와 개인 성향 점수, 대상 지역·출현 위치·중요도·노출 순서를 실행 데이터로 정리해야 한다. 파일의 존재가 DB 등록 완료를 뜻하지 않는다.

- 개인 점수에 ±3, -4가 있는데 현재 DB의 NORMAL은 ±1, MAJOR는 ±2이고 선택 원장도 ±2만 허용한다. 원문 점수를 보존하는 스키마/규칙 마이그레이션을 준비하고 기존 회차 규칙은 유지한다. 콘텐츠를 몰래 ±2로 잘라 넣지 않는다.
- 30문항에 기존 성향 경계 ±3을 그대로 쓰면 분포가 크게 달라질 수 있다. 원문 점수와 응답 수별 결과 분포를 시뮬레이션하고 새 회차 규칙을 조정한다. 임계값 숫자는 실험 전 임의 확정하지 않는다.
- `admission_buffer > 0` DB 제약 때문에 0초 마감은 설정 변경만으로 구현되지 않는다. 신규 마이그레이션·준비 검사·화면 안내·경계 테스트가 필요하다. 이미 배포된 001 파일을 고쳐 기존 DB 적용을 대신하지 않는다.
- 웹 푸시 미응답자도 포함하려면 첫 성공 선택에 의존하던 회차 가입을 입장 시점으로 옮기고, 회차 동의/구독과 무응답 결과를 저장해야 한다.

### 위임에 따른 설계 기준 — 구현 전

1. **도시 표현은 연속 변화+핵심 임계치의 혼합 방식**을 채택한다. 20점마다 도시 전체를 일괄 교체하는 대신 색·조명·안개·군중 반응은 부드럽게 변화시키고, 쓰레기 더미·시설 상태 등 분명한 사건은 임계치에서 표현한다. 스탯별 낮음/기본/높음 자산을 조합해 제작량을 제어한다. 오염은 높은 값이 악화 방향이다.
2. 초기 시험 임계값은 30/70 후보, 복귀에는 약 3점 여유를 두어 경계 왕복에 따른 깜빡임을 방지한다. 정확한 경계·효과 강도는 500명과 콘텐츠 30개를 기준으로 보정한다. 고정 수치 확정이나 성능 통과 판정은 아니다.
3. 최종 도시는 회차의 확정 수치·map/visual-rule 버전·자산 버전에 묶는다. 실시간 전환 이력이 최종 결과에 영향을 주면 그 상태도 저장하고, 그렇지 않으면 확정 수치로 결정론적으로 재구성한다. 다음 회차의 맵/표현 변경이 과거 결과를 바꾸지 않게 한다.
4. 회차 종료는 DRAIN 유지. 새 회차는 도시 50/50/50, 지역 오염 0, 개인 점수 0에서 시작하고 기존 결과를 보존한다. 개인 자격은 유지하되 학과·선택·NPC·구독 대상은 회차별로 구분한다. 0응답 가입자는 ‘참여한 선택 없음’ 결과를 제공한다.
5. 다른 기기 조회는 회차별 **비밀 결과 링크/복구 코드**를 제공하는 방향으로 설계한다. 공개 UUID만으로 본인 결과를 열지 않는다. 충분한 난수 자격·서버 해시·조회 전용 권한·요청 제한을 사용하고 URL 로그/외부 전송 노출을 줄인다. 링크를 가진 사람은 볼 수 있음을 사용자에게 알린다. 푸시 수신 자체는 구독한 기기에 한정되고, 링크를 다른 기기로 옮겨 결과를 여는 기능과 구분한다.
6. 결과 공개 직후 회차+수신자+채널 기준으로 발송 작업을 생성한다. 미응답 여부와 무관하게 유효한 동의/구독을 대상으로 하고 동의 철회·만료 구독은 제외한다. 재시도·중복 억제·실패 기록을 갖추되 OS/브라우저 사정으로 실제 도착 시각이나 전원 수신을 보장하지 않는다.
7. 학과는 사용자 목록 직접 선택, 기타/외부/선택안함 제공, 첫 선택 후 회차별 고정. 성향 통계는 종료 후 공개, 상세 5명 미만 숨김. 정수아가 위임한 운영 기본안으로 채택하되 실제 API 보호는 후속 구현이다.
8. 결과 조회는 전시 종료 후 최소 30일 유지하는 운영 기준으로 준비한다. 기간 종료 시 자동 삭제는 수행하지 않으며 실제 삭제·장기 보관은 별도 정책으로 명시한다. 운영 백업은 일일 및 행사 전후, 외부 위치 보관·복원 시험을 포함한다. 무료 서비스가 이 운영 조건을 충족하는지는 별도 검증한다.
9. 영향 배율은 현 0.1을 운영값으로 확정하지 않는다. 500명×예상 응답 수와 실제 30개 콘텐츠로 편향된 선택/균등 선택/저참여 시나리오를 검증해 조정한다. 참가자가 적어도 개별 캐릭터 반응은 즉시 보이도록 하고 집계 수치를 임의 부풀리지 않는다.

### 추가 확인 완료 — iPhone 푸시와 선택 종료

- **iPhone 웹 푸시: 안내 승인.** 일반 브라우저 참여는 그대로 제공하고, 푸시를 원하는 iPhone 사용자에게만 홈 화면 추가·실행·권한 허용을 안내한다. 홈 화면 추가나 알림 동의는 참여 조건이 아니다. Apple 지원 조건은 [공식 문서](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers)를 따른다. 실제 구독/수신 검증은 후속 구현이다.
- **회차 종료 후 선택: 불가로 확정.** 개별 질문에는 시간제한이 없지만 회차 종료 순간 신규 입장·선택 접수를 함께 닫는다. 종료 전 입장자에게도 추가 응답 유예를 주지 않는다. 자동 종료 정각부터 거부하며 5초 선마감은 없앤다. 이미 성공한 요청의 재조회는 허용하되 재반영하지 않는다.
- DRAIN은 종료 전에 처리 중이던 DB 작업을 완료 또는 롤백하여 결과를 확정하는 내부 처리다. 종료 후 사용자에게 선택 기회를 연장하는 기능이 아니다. 최종 확정 뒤에는 도시/NPC/오염 상태를 동결하고 결과 조회·알림만 제공한다.
- 인수 검사: 일반 iPhone 탭 참여, 홈 화면에서 권한 허용/거부·구독·실제 푸시, 홈 화면 전환 시 본인 회차 연결, 종료 직전/정각/직후 입장·선택, 종료 전 열린 패널의 늦은 제출 거부, 성공 요청 재전송의 중복 반영 없음, FINALIZED 불변. 모바일 참여 세션과 홈 화면 웹 앱의 저장소가 같다고 가정하지 않고 안전한 연결 절차를 구현한다.

### 자산 질문의 뜻과 일정 영향

‘사용 가능한 원본 자산’은 이미 만든 Blender 맵·캐릭터 모델·이미지가 있는지를 뜻했다. 저장소의 Neighborhood 맵/FBX/GLB는 확인했으므로 재사용한다. 민경의 추가 캐릭터/도시 효과 제작 가능 시간과 납기는 아직 모른다.

전체 기능은 유지하되 이메일·사용자 다운로드 저장만 선택 범위로 구분한다. 선택지 점수 마이그레이션, 입장/무응답자 처리, 타기기 결과 자격, 푸시 구독·발송, 0초 선마감 지원을 작업 목록에 추가한다. 모바일 렌더링 방식은 기존과 같이 성능·재미 실측 후 선택한다. 이번 변경은 결정 문서 반영이며 서버/DB/푸시 구현이나 런타임 검증을 완료한 것이 아니다.
