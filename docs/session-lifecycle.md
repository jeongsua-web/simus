# 회차 운영과 결과 계산 규칙

조사 기준: 2026-09-16, 저장소의 DB 정의와 서버 코드. 운영 DB에 접속해 실제 배포 상태를 확인한 문서는 아니다.

구현 갱신: `db/002_session_lifecycle.sql`과 회차 운영 API가 이 문서의 제안을 구현했다. 적용된 제품 규칙은 규칙 스냅샷 v1에 명시하도록 했으며, 축 방향·9종 해석·초기값·무응답 포함 여부가 빠진 회차는 시작하지 않는다. 종료 중인 선택은 `completion_policy: DRAIN`에 따라 회차 잠금 앞에서 완료 또는 롤백될 때까지 기다린 뒤 확정한다. 상세 API와 자동 종료 실행법은 [API 문서](../web/API.md)를 따른다.

이 문서의 **현재 구현**은 코드·DB 제약으로 확인한 동작, **기존 설계**는 저장소 문서에 명시됐지만 서버 구현이 없는 요구사항, **구현 제안**은 이를 연결하기 위한 처리 방식이다. **결정 필요**는 제품 규칙 또는 운영 보장 수준을 추가로 확정해야 하는 항목이다.

## 2. 회차 상태와 허용 전이

DB의 상태 값은 `DRAFT`, `RUNNING`, `CLOSING`, `FINALIZED` 네 가지다. 아래는 **구현 제안인 허용 전이**이며, DB에는 이전 상태와 새 상태를 비교해 이 순서를 강제하는 트리거가 없다.

| 전이 | 조건과 처리 |
| --- | --- |
| `DRAFT → RUNNING` | 관리자 인증, 시작 검증 및 초기 상태 생성 성공 후 같은 트랜잭션에서 `starts_at` 설정 |
| `RUNNING → CLOSING` | 수동 또는 자동 종료 승인. 접수 차단과 종료 사유·시각을 저장하고 확정 준비 |
| `CLOSING → FINALIZED` | 진행 중 선택 정리, 전체 결과 저장 완료와 함께 원자적으로 전환 |

역방향 전이, 단계 건너뛰기, 확정 회차 재개는 허용하지 않는 것을 제안한다. 동일 요청 재시도는 새 전이 없이 기존 처리 결과를 반환한다. 일시정지·취소 상태는 DB에 없으므로 필요 여부는 별도 결정 대상이다.

현재 DB가 보장하는 사항:

- `RUNNING` 또는 `CLOSING`은 전체에서 합쳐 최대 1개다(`one_active_session`). 종료 복구가 끝나기 전에는 다음 회차를 시작할 수 없다.
- `DRAFT`가 아니면 `starts_at`이 필요하다. 시작 시각이 있으면 `scheduled_end_at > starts_at + admission_buffer`여야 한다.
- `CLOSING`/`FINALIZED`에는 `end_mode`, `admission_closed_at`, `end_requested_at`이 필요하다.
- `FINALIZED`에는 추가로 `actual_ended_at`, `finalized_at`이 필요하다.
- `AUTO`는 종료 관리자 ID가 없어야 하고, `MANUAL`은 있어야 한다. FK는 관리자 활성 여부까지 검사하지 않는다.
- 상황·선택지·지역·지역 영향은 `DRAFT`에서만 편집 가능하다. 콘텐츠 트리거도 부모 회차를 `FOR UPDATE`로 잠근다.

DB는 시각의 전체 선후관계, 상태 전이 순서, 시작 후 회차 설정 고정, 결과 행 완전성을 보장하지 않는다. `FINALIZED`여도 상태 테이블 갱신 및 새 결과 행 삽입을 상태 기준으로 막는 제약은 없다. 원장·결과의 기존 행 UPDATE/DELETE/TRUNCATE 금지와는 별개의 문제다.

## 3. 시작 전 검증

**구현 제안:** 회차 행을 `FOR UPDATE`로 잠근 뒤 `DRAFT`를 재확인하고, 아래 검증·초기화·상태 전환을 하나의 트랜잭션으로 처리한다. 다른 회차와의 시작 경쟁은 부분 유일 인덱스 충돌까지 처리한다. 하나라도 실패하면 시작 전체를 롤백한다.

| 대상 | 검증 조건 및 근거 |
| --- | --- |
| 상황·선택지 | 상황이 존재하고 각 상황에 선택지가 2개 이상이어야 한다. 선택지 2개 이상은 기존 DB 설명의 요구이며 SQL 제약은 아니다. 회차별 코드 중복 및 회차가 다른 FK는 DB가 차단한다 |
| 개인 영향 | `NORMAL`은 각 축 -1~1, `MAJOR`는 -2~2. DB가 범위를 검사한다. `MAJOR`에 추가 배수를 적용하지 않는다 |
| 지역 | 1개 이상, 가중치는 유한한 양수. 모든 지역에 초기 상태가 생겨야 한다. 일부 지역 상태가 빠지면 전체 오염 뷰가 그 지역을 제외하고 계산하므로 누락을 허용하지 않는다 |
| 지역 영향 | 선택지·지역이 동일 회차 소속인지 확인한다. 현재 구현은 영향 행이 있는 지역만 갱신한다. 행이 없으면 그 지역 변화가 없다. 모든 선택지×지역 조합의 명시적 0행을 요구할지는 결정 필요 |
| 숫자·보정 | 기본 영향과 `impact_scale`의 유한성, 저장 가능한 곱의 범위·정밀도 확인. 예상 참여자·1인 예상 응답 수는 양수, 계수는 0 이상. 현재 선택 API의 일부 `NaN` 거부는 시작 검증을 대체하지 못함 |
| 시간 | 서버/DB가 정한 시작 시각에 대해 종료 시각이 버퍼보다 충분히 뒤인지 확인. `admission_buffer > 0`, 기본 5초. 예약 시작 기능 자체는 미구현 |
| 초기값 | 도시 3개 지표와 지역 오염이 모두 유한한 0~100 값인지 검사. 상태가 이미 있으면 값·행 수·버전 및 기존 원장 유무를 검증하고 불일치를 덮어쓰지 않음 |
| 규칙 스냅샷 | JSON 객체라는 DB 검사 외에 아래 의미 검증 필요 |

규칙 스냅샷의 **기존 근거**는 seed의 `alignment_thresholds: {negative: -3, positive: 3}`, `initial_city_state`와 DB 설명의 “해석은 해당 회차 규칙에서 복사”다. seed에는 축 방향, 9종 해석 문구, 지역 초기값이 없으므로 완성된 운영 규칙 샘플로 볼 수 없다.

**구현 제안:** 규칙 버전, 축 의미·부호 방향, 성향 경계, 9종 코드별 해석 문구, 도시·지역 초기값을 검증 가능한 계약으로 정의한다. 키 이름과 구조는 아직 미정이다. 별도 컬럼인 `impact_scale`, 예상 인원·응답 수, `pollution_aggregation` 등을 JSON에도 담는다면 일치 검사를 둔다. 시작 후 시간·버퍼·계수·규칙·가중치 등 결과에 영향을 주는 설정을 고정한다. 현재 회차 테이블에는 이 고정을 강제하는 트리거가 없다.

**결정 필요:** 기본 영향의 허용 범위, 예상 인원·응답 수에서 `impact_scale`을 도출하는 공식, 예상 수치가 실제 참여 제한인지 여부. 현재 코드는 저장된 계수를 그대로 곱하며 예상 수치를 입장 제한이나 응답 할당량으로 사용하지 않는다.

## 4. 시작 시 상태 생성

시작 트랜잭션에서 다음을 준비한 뒤 `RUNNING`으로 전환하는 것을 제안한다.

| 테이블 | 초기화 |
| --- | --- |
| `city_states` | 회차당 1행. DB 기본값은 행복·안전·청결 각각 50, `version=0`. 확정한 스냅샷 초기값을 사용하고 값이 일치하는지 검증 |
| `region_states` | `session_regions`의 모든 지역당 1행. DB 기본 오염은 0. 별도 초기값 정책은 결정 필요 |
| `participant_sessions` | 사전 등록자가 있다면 해당 회차 가입 행. 현재는 첫 성공 선택 때 생성 |
| `participant_alignments` | 가입자마다 `x_score=0`, `y_score=0`, `response_count=0`. 기존 성공 선택 경로처럼 가입 행과 함께 생성 |

현재 익명 참여자 생성은 전역 `participants`/`participant_credentials`만 생성한다. 시작 시 모든 전역 참여자를 새 회차에 자동 등록해서는 안 된다. 현 구현을 유지하면 시작 당시 가입자가 없어 개인 상태도 없으며, 첫 선택 트랜잭션에서 지연 생성한다.

**결정 필요:** 별도 회차 입장 기능·사전 등록을 추가할지, 접속만 하고 응답하지 않은 사람도 결과 대상인지. 현재 정상 API 흐름에서 실패한 선택은 가입·개인 상태 생성까지 롤백되므로, 0응답 가입자는 일반적으로 생기지 않는다.

## 5. 선택 마감과 수동·자동 종료

현재 접수 가능 조건은 다음과 같다. 클라이언트 시각·클라이언트 점수는 사용하지 않는다.

```text
status = RUNNING
AND starts_at <= DB clock_timestamp()
AND admission_closed_at IS NULL
AND DB clock_timestamp() < scheduled_end_at - admission_buffer
```

`auto_cutoff_at = scheduled_end_at - admission_buffer`이며 그 시각과 같아지면 새 선택을 거부한다. 별도 작업이 실행되지 않아도 시간 조건으로 접수는 막히지만, 상태가 자동으로 `CLOSING`/`FINALIZED`로 바뀌거나 마감 시각 컬럼이 채워지지는 않는다.

**구현 제안:** 자동 접수 마감과 회차 종료를 구분한다. 자동 마감부터 예정 종료까지 `RUNNING`이면서 `accepting_choices=false`일 수 있다. 예정 종료 시점에 자동 종료 작업이 `CLOSING`으로 전환한다. 수동 종료는 승인 시 접수를 닫고 `CLOSING`으로 전환하여 동일한 결과 확정 절차로 진입한다.

| 컬럼 | 제안하는 의미 |
| --- | --- |
| `scheduled_end_at` | 예정 종료 시각. 실제 처리 완료 시각과 구분 |
| `admission_closed_at` | 유효 접수 차단 시각. 자동은 cutoff, 수동은 승인 시각과 cutoff 중 이른 시각 |
| `end_requested_at` | DB에 받아들인 종료 요청 시각. 자동 작업이 늦게 실행된 경우 예정 시각과 구분 |
| `actual_ended_at` | 미완료 선택을 정리하고 더 이상 상태 변화가 없음을 확인한 시각 |
| `finalized_at` | 결과 저장 및 확정에 사용하는 공통 DB 시각. 커밋 후 공개하며 정확한 물리적 커밋 시각을 뜻하지 않음 |

이 컬럼들의 세부 의미는 DB 제약만으로 확정되지 않으므로 구현 전에 합의해야 한다. 이미 닫힌 접수의 시각을 늦추거나 재개하지 않는다.

수동·자동 종료 경쟁은 같은 회차 잠금으로 직렬화하고, 먼저 저장된 종료 메타데이터를 재시도가 덮어쓰지 않도록 제안한다. 다만 예정 시각을 지난 수동 요청을 항상 `AUTO`로 볼지, 최초 승인 요청 기준으로 볼지는 **결정 필요**다. `admin_actions`는 관리자 작업용이므로 자동 작업에 가짜 관리자 ID를 넣지 않는다.

## 6. 진행 중 선택과 종료의 조정

### 현재 보장과 한계

선택 API는 인증 후 회차 행을 `FOR UPDATE`로 잠그고 커밋/롤백까지 유지한다. 같은 회차의 선택들은 직렬화된다. 동일 요청 키를 먼저 조회하므로 이미 성공한 동일 본문은 마감 후에도 200으로 재응답하며 새 상태 변화는 없다. 같은 키·다른 본문은 거부한다.

새 선택은 접수 검사 → 콘텐츠·상태 검증 → 가입·개인 상태 생성 → 도시·원장·개인·지역 갱신 → 접수 재검사 → 커밋 순서다. 마지막 검사에서 cutoff를 넘으면 전체 롤백된다. `received_at`은 HTTP 도착 시각이 아니라 잠금 획득과 검증 후 원장 생성 SQL에서 얻는 DB 시각이다. 마감 전에 도착한 요청이라고 반드시 접수되는 것은 아니다.

현재 공통 함수의 `lock_timeout=5s`, `statement_timeout=10s`는 각각 잠금 대기·개별 SQL 제한이다. 전체 트랜잭션이나 커밋의 절대 종료 시각 보장이 아니며, 마지막 검사와 `COMMIT` 사이에도 틈이 있다. 기본 접수 버퍼 5초만으로 엄격한 종료를 보장할 수 없다.

### 구현 제안: 공통 잠금과 두 단계 종료

1. 모든 선택·가입·운영 상태 변경 경로가 회차 잠금을 먼저 얻도록 통일한다. 종료 작업도 회차 행 잠금을 얻고 상태를 다시 읽는다. 기존 선택이 잠금을 보유했다면 그 선택의 커밋/롤백을 먼저 확인한다.
2. 잠금을 얻은 종료 작업은 접수 차단, 종료 메타데이터, `CLOSING`을 한 트랜잭션으로 저장한다. 이후 대기 중인 새 선택은 잠금을 얻어도 상태 검사에서 거부된다.
3. 별도 확정 트랜잭션이 같은 회차 잠금을 얻어 `CLOSING` 및 상태·원장 일관성을 확인하고, 모든 결과와 `FINALIZED`를 함께 저장한다. 결과 산출 중 잠금을 유지하고 모든 쓰기 경로가 종료 상태를 존중하도록 한다.
4. 종료 잠금 획득이 timeout으로 실패하면 성공 응답을 보내지 않고 재시도한다. 장시간 대기 트랜잭션을 감지·정리할 수 있게 한다. 현재 helper는 timeout을 일반 500으로 반환하므로 운영용 오류·재시도 계약이 추가로 필요하다.

이 방식은 **확정 결과에 이후 선택이 섞이지 않는 일관성**을 제공하지만, 수동 종료 HTTP 요청 순간이나 예정 종료 시각 이후의 커밋을 모두 차단한다는 보장은 아니다. 수동 종료가 잠금을 기다리는 동안 기존 선택은 아직 종료 요청을 볼 수 없다.

### 결정 필요: 종료 시각의 엄격성 및 취소 정책

DB 설명은 미완료 트랜잭션 취소 조정을 후속 필수 사항으로 명시하지만, 취소 기준과 허용 지연은 구현되어 있지 않다. 다음 중 어떤 정책인지 먼저 확정해야 한다.

- **처리 정리 후 확정:** 이미 처리 중인 선택이 현재의 마감 재검사를 통과하면 완료를 허용하고, 실제 종료 시각은 정리 완료 시각으로 기록한다. 정해진 시각보다 확정이 늦을 수 있다.
- **미완료 선택 취소:** 수동 승인 또는 자동 종료 경계에서 아직 완료되지 않은 선택을 롤백한다. 별도의 종료 조정기가 선택 연결/트랜잭션을 식별하고, 새 실행을 막은 뒤 대상만 취소·필요시 연결 종료하고 잠금 해제를 확인해야 한다. 이미 커밋된 선택은 취소할 수 없다.

두 번째 정책에는 여러 서버 인스턴스가 공유하는 접수·커밋 조정 방식과 재시작 가능한 작업 추적이 필요하다. 회차 잠금 뒤에서 종료 플래그를 쓰는 것만으로는 잠금 보유자를 취소할 수 없다. SQL 취소만으로 유휴 트랜잭션이나 이미 진행 중인 커밋까지 안전하게 해결했다고 간주해서도 안 된다. 연결 식별 정보의 재사용을 검증하고 해당 선택 트랜잭션만 대상으로 해야 한다.

정확한 벽시계 시각 이후 커밋을 금지하는 요구라면 커밋 승인과 종료를 조정하는 별도 설계·장애 검증이 필요하다. 현재 스키마·행 잠금·시간 검사 또는 취소 요청 하나만으로 그 보장을 선언하지 않는다. DB 소유자 권한을 일반 웹 요청에 부여하는 방식도 사용하지 않는다.

## 7. 최종 점수와 9종 성향

### 확인된 계산 규칙

- 개인 점수는 성공적으로 반영된 선택의 `alignment_dx`, `alignment_dy` 합이다. `response_count`는 해당 원장 수다. `impact_scale`은 개인 점수에 곱하지 않는다.
- 개인 점수는 `bigint`이며 0~100 제한·평균화·응답 수 보정이 없다. 계산·API 직렬화 시 JavaScript `number`로 무손실 처리할 수 있다고 가정하지 않는다.
- [DB 설명](../db/README.md)에 각 축 **-3 이하 / -2~2 / 3 이상**의 경계가 명시되어 있다. seed에도 -3, 3이 있다. DB 자체에는 이 판정 함수나 점수-코드 일치 제약이 없다.
- 판정은 최종 합계를 대상으로 한다. 경계를 바꾸거나 응답 수로 정규화하는 것은 기존 설계 변경이다.

**결정 필요:** X/Y 중 어떤 축이 질서/혼돈, 선/악인지와 각 부호의 방향. seed의 분리배출 선택이 `(+1,+1)`인 것만으로 축 의미를 확정할 수 없다.

아래는 **X 양수=질서, X 음수=혼돈 / Y 양수=선, Y 음수=악으로 합의했을 때만 적용할 조건부 매핑**이다. 모든 코드는 현재 DB에 정의되어 있다.

| 최종 X \\ 최종 Y | Y ≤ -3 | -2 ≤ Y ≤ 2 | Y ≥ 3 |
| --- | --- | --- | --- |
| X ≤ -3 | `CHAOTIC_EVIL` | `CHAOTIC_NEUTRAL` | `CHAOTIC_GOOD` |
| -2 ≤ X ≤ 2 | `NEUTRAL_EVIL` | `TRUE_NEUTRAL` | `NEUTRAL_GOOD` |
| X ≥ 3 | `LAWFUL_EVIL` | `LAWFUL_NEUTRAL` | `LAWFUL_GOOD` |

해석은 회차 규칙에서 해당 코드의 문구를 복사한다는 것이 기존 설계다. 문구 자체와 저장 JSON 경로는 미정이다. 종료 때 임의 생성하거나 최신 공용 문구를 참조하면 과거 결과가 달라질 수 있으므로, 시작 전에 9종 문구를 준비하고 스냅샷으로 고정하는 것을 제안한다.

0응답 결과를 저장한다면 DB상 X/Y는 모두 0이어야 한다. 위 매핑에서는 `TRUE_NEUTRAL`이지만 DB가 이 코드까지 강제하지 않는다. 0응답자를 결과에 포함할지와 “응답 없음” 해석을 따로 둘지는 결정 필요다.

### 결과 저장 제안

확정 트랜잭션 안에서 다음을 수행한다.

1. 회차를 잠그고 `CLOSING`을 확인한다. 도시 1행, 모든 지역 상태, 결과 대상 가입자별 개인 상태가 존재하는지 검사한다. 누락을 0으로 대체해 확정하지 않는다.
2. 개인 합계·응답 수를 `choice_records`의 합계·개수와 대조한다. 도시 버전과 원장의 버전·개수 일관성도 확인한다. 불일치는 확정을 중단하고 복구 대상으로 남긴다. 도시·지역은 선택 순서별 제한이 적용되므로 기본 영향 총합만 더해 재계산하면 안 된다.
3. `session_results`에 도시 3개 지표, `final_state_version`, 전체 오염, `rules_snapshot`, 공통 `finalized_at`을 저장한다. 전체 오염은 기존 방식인 `Σ(지역 오염 × aggregation_weight) / Σ(aggregation_weight)`이며 모든 지역 상태가 갖춰진 뒤 DB numeric으로 계산한다.
4. `region_results`에 모든 지역의 최종 오염을 저장한다.
5. `participant_results`에 결과 대상자의 최종 X/Y, 응답 수, 판정 코드, 스냅샷에서 복사한 `interpretation`, 동일 확정 시각을 저장한다. 결과 대상은 전역 참여자가 아니라 해당 회차의 가입자 집합을 기준으로 정한다.
6. `actual_ended_at`과 `finalized_at`을 설정하고 회차를 `FINALIZED`로 전환한다. 관련 관리자 작업의 성공 상태도 승인/완료 계약에 맞춰 갱신한다. 모든 삽입·전환을 함께 커밋한다.

결과 PK는 회차당 도시 결과 1개, 지역·참여자당 1개다. 결과 행은 수정 불가이므로 덮어쓰기 UPSERT를 사용하지 않는다. 충돌을 무조건 `DO NOTHING`으로 무시하면 부분 결과를 완전한 것으로 오인할 수 있다. 재시도는 회차 잠금 뒤 확정 상태와 결과 완전성을 확인해서 성공을 반환한다.

확정 후 공개 도시는 결과 테이블에서 읽도록 전환하거나 상태 테이블의 불변성을 별도로 강제해야 한다. 현재 `/api/city-state`가 확정 회차에도 가변 상태를 조회한다는 점을 후속 구현에 반영한다.

## 8. 종료 중 서버 재시작 복구

**구현 제안:** 프로세스 메모리의 타이머가 아닌 DB 상태를 복구의 기준으로 삼는다. 시작 시와 주기 작업에서 대상 회차를 검색하고, 각 처리 직전에 회차 잠금을 얻어 상태를 재확인한다. 여러 작업자가 같은 회차를 발견해도 이 잠금과 결과 PK로 중복 확정을 막는다.

| 재시작 시 DB 상태 | 복구 처리 |
| --- | --- |
| `RUNNING`, cutoff 전 | 정상 접수 유지 및 자동 종료 작업 재등록 |
| `RUNNING`, cutoff 이후·예정 종료 전 | 시간 조건으로 접수 거부 유지. 마감 메타데이터를 보완하고 종료 예약 복구 |
| `RUNNING`, 예정 종료 이후 | 자동 종료 절차 실행. 예정 시각과 실제 복구·종료 시각을 구분해 기록 |
| `CLOSING` | 기존 사유·관리자·접수 차단 시각 보존. 남은 선택 정리 후 확정 트랜잭션 재실행 |
| `FINALIZED`, 결과 완전 | 아무것도 재계산하지 않고 저장된 결과 반환 |
| `FINALIZED`인데 결과 누락, 또는 `CLOSING`에 부분 결과 존재 | 정상 원자적 저장 경로에서는 발생하지 않아야 함. 자동 덮어쓰기 없이 정합성 오류로 보고하고 조사 |

`CLOSING` 저장 전에 죽으면 해당 트랜잭션은 롤백되어 이전 상태에서 다시 판단한다. `CLOSING` 저장 후 확정 도중 죽으면 확정 트랜잭션 전체가 롤백되고 `CLOSING`에서 재시도한다. 커밋 후 응답 전에 죽으면 재시도가 이미 저장된 `FINALIZED`를 반환한다.

연결이 완전히 끊기기 전까지 DB 트랜잭션과 잠금이 남아 있을 수 있으므로, 서버 재시작 자체를 롤백 완료의 증거로 삼지 않는다. 잠금 획득·연결 종료 확인과 재시도 제한·운영 알림이 필요하다. 미완료 선택을 재전송할 때는 기존 `request_key`를 유지하고, 이미 반영됐으면 기존 원장을 반환한다.

`admin_actions`의 `PENDING`은 성공으로 간주하지 않는다. 회차 상태·동일 요청 키·작업 내용을 대조해 재개하거나 완료 상태를 복구한다. 관리자 키의 유일성은 `(admin_id, request_key)`이므로 다른 회차/작업에 같은 키를 재사용하면 충돌 처리해야 한다. `SUCCEEDED`를 종료 승인 시점으로 볼지 결과 확정 완료로 볼지는 **결정 필요**이며 API 응답도 그 의미를 구분해야 한다.

## 9. 인증과 조회 권한

### 관리자

현재 `admin_users`는 외부 인증 제공자의 불변 식별자 `auth_subject`와 `is_active`를 저장한다. `admin_actions`에는 `CREATE`/`START`/`END`, 요청 키, 요청·승인 시각과 결과 상태가 있다. 실제 외부 인증 검증, 관리자 API, 감사 기록 작성은 미구현이다. 개발 seed의 `dev-admin`은 로그인 수단이 아니다.

**구현 제안:** 서버가 외부 인증을 검증한 뒤 신뢰한 subject로 활성 관리자 행을 찾아 회차 생성·시작·종료를 허용한다. 클라이언트가 보낸 관리자 UUID·이메일·표시 이름만으로 권한을 부여하지 않는다. 변경 요청의 출처/CSRF 방어, 요청 키와 회차·작업의 일치 검사, 감사 기록을 적용한다. 외부 인증 제공자와 관리자별 세부 권한은 결정 필요다.

현재 DB의 PUBLIC 권한 회수는 최소 권한 운영 역할 설정이나 HTTP 인증을 대신하지 않는다. 배포용 역할 분리 및 결과·상태 쓰기 제한이 필요하며, 관리자에게 타인의 개인 결과를 조회할 권한이 자동으로 부여된다고 해석하지 않는다.

### 참여자와 본인 결과

현재는 32바이트 난수 토큰의 64자리 hex 값을 `simus_participant` 쿠키로 발급한다. HttpOnly, SameSite=Lax, 운영 환경 Secure, 만료 30일이며 DB 해시·만료·폐기 여부로 참여자를 인증한다. 기존 쿠키 재사용은 만료를 연장하지 않는다.

본인 결과 API는 미구현이다. **구현 제안:** 유효한 쿠키로 얻은 참여자 ID와 요청 회차 ID를 함께 사용해 `participant_results`를 조회하고, 회차가 `FINALIZED`일 때만 반환한다. URL/본문의 참여자 ID는 본인 인증 근거로 사용하지 않는다. 종료 전 개인 점수·중간 성향·숨겨진 선택 영향은 계속 비공개로 유지한다. 결과 응답은 캐시하지 않는다.

미인증·만료는 401, 타인의 ID를 지정한 접근은 조회를 허용하지 않으며, 미확정/본인 결과 없음의 응답 형식은 API 계약으로 정한다. 쿠키 분실·만료 후 과거 결과 복구 정책은 **결정 필요**다. 현재 코드는 기존 토큰 없이 이전 참여자 신원을 복구하는 수단을 제공하지 않는다.

## 10. 구현 착수 전 결정 목록과 후속 검증

우선 결정할 항목은 축 의미·부호 방향과 9종 해석 문구, 규칙 JSON 계약, 초기값·계수 정책, 0응답 결과 대상, 수동·자동 종료 경쟁 우선순위, 미완료 선택 취소 기준과 종료 시각 보장 수준, 관리자 인증 제공자, 익명 자격 만료 후 결과 접근 정책이다. 이 항목을 개발 seed나 필드 이름만으로 확정하지 않는다.

후속 구현에서는 최소한 다음을 검증한다. 이번 문서 작업에서는 서버 변경이나 DB 변경 테스트를 실행하지 않았다.

- 시작 검증 실패의 전체 롤백, 동시 시작 경쟁, 시작과 콘텐츠 편집 경쟁, 모든 지역 초기화.
- cutoff 직전/동일/직후 선택, 잠금 대기 중 마감, 종료와 선택·재시도 경쟁, timeout·취소·커밋 응답 유실.
- 각 축 -3/-2/2/3 경계 및 9개 조합, `MAJOR` 영향·무응답 정책·해석 복사·bigint 정밀도.
- 가중 오염과 지역 누락 차단, 결과 일괄 저장, 확정 후 상태 변경·추가 결과 삽입 차단.
- `CLOSING` 저장 전후·결과 커밋 전후 재시작, 여러 종료 작업자의 경쟁과 멱등성.
- 비활성 관리자·위조 관리자 ID·타인 결과·미확정 결과 접근 거부 및 인증 만료 처리.
